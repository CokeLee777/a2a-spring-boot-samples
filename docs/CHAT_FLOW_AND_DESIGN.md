# 채팅 흐름 정리 및 대화형 설계 방안

## 1. 현재 채팅 흐름

### 전체 흐름도

```
[사용자] → POST /chat { message, sessionId? }
    ↓
[a2a-client 8080]
    ├─ sessionId 없음 → 새 UUID 생성
    ├─ ChatMemory (sessionId 기준, 최대 20메시지) 에서 대화 이력 로드
    ├─ ChatClient.prompt().user(message).call()
    │     ├─ LLM이 메시지 + 대화 이력 보고 도구 호출 여부 결정
    │     ├─ 도구 호출 시: OrderTools / DeliveryTools → A2A 프로토콜로 에이전트 호출
    │     └─ 도구 결과를 LLM에 돌려주고 최종 자연어 응답 생성
    └─ 응답 + sessionId 반환 (대화 이력에 이번 턴 추가)
```

### 클라이언트 측 (이미 “채팅식” 가능)

| 요소 | 역할 |
|------|------|
| **ChatRequest.sessionId** | 세션 식별. 같으면 같은 대화로 간주. |
| **ChatMemory** | `MessageWindowChatMemory`로 sessionId별 최근 20메시지 유지. |
| **MessageChatMemoryAdvisor** | 매 요청 시 해당 세션의 이전 대화를 LLM에 함께 전달. |
| **Tools** | `checkOrderCancellability(OrderRequest)`, `trackDelivery(DeliveryRequest)` — LLM이 도구를 골라 **현재 턴의 인자만** 넘김. |

즉, **클라이언트는 이미 세션·대화 이력**을 갖고 있어서  
“ORD-1001 취소 가능해?” → “가능해요” → “그럼 취소 진행해줘”처럼 **이전 맥락을 LLM이 이해**할 수 있는 구조다.

### 서버 측 (a2a-server) — 단답형인 이유

| 단계 | 동작 |
|------|------|
| **진입** | `*AgentExecutorProducer.execute(@RequestBody String body)` — JSON-RPC `SendMessage` 한 건만 처리. |
| **파싱** | `extractText(params)` 로 **현재 메시지의 텍스트 한 개만** 추출. `sessionId`, `conversationId`, 이전 대화 없음. |
| **라우팅** | `canHandle(userText, isInternalCall)` → 해당하는 `SkillExecutor` 한 개 선택. |
| **실행** | `execute(userText, isInternalCall)` → **입력 문자열 하나 → 응답 문자열 하나** (무상태). |

즉, 에이전트는 설계상 **“이번 턴의 사용자 발화 한 문장”만 보고, 한 번의 스킬 실행 결과(문자열)만 반환**한다.  
세션·대화 이력·후속 질문 처리가 없어서 **단답형**으로만 동작한다.

### 요약

- **대화형으로 이어지는 부분**: 클라이언트의 **세션 + ChatMemory + LLM** (이전 메시지로 “그 주문”, “그거” 등 해석).
- **단답형인 부분**: **a2a-server**는 요청당 메시지 한 개만 받고, 이력 없이 한 번만 실행해서 한 문장으로 답하는 구조.

## 2. 채팅식으로 흘러가게 하는 설계 방안

### 방안 A: 클라이언트 책임 확대 (현 구조 유지, 권장)

**아이디어**: 에이전트는 계속 **“단일 질의 → 단일 응답”**만 담당하고, **대화형 흐름은 클라이언트의 메모리 + LLM**이 담당한다.

- 사용자: “ORD-1001 취소 가능해?” → 도구 호출 → “취소 가능합니다.”
- 사용자: “그럼 취소 진행해줘” → LLM이 대화 이력으로 ORD-1001을 알고, “취소 진행” 도구가 있으면 해당 도구 호출 또는 “취소는 별도 절차가 필요합니다” 등으로 응답.

**필요한 작업**

- 시스템 프롬프트 보강: “이전 대화에서 언급된 주문번호·운송장번호를 재사용할 수 있다”, “후속 요청(취소 진행, 배송 변경 등)은 맥락을 보고 판단한다” 등.
- 필요 시 **도구 추가**: 예) `requestOrderCancellation(OrderRequest)` 등 “진행” 액션을 넣으면, LLM이 이력 + 도구로 채팅식으로 응답 가능.

**장점**: 서버 단순 유지, A2A 스펙·서버 API 변경 없음.  
**단점**: “진짜 취소 처리”처럼 서버에 없는 액션은 LLM이 말로만 안내하게 됨.

---

### 방안 B: 서버에 세션·대화 맥락 도입

**아이디어**: A2A 요청에 **conversationId(sessionId)** 를 넣고, 서버가 **세션별 대화 이력**을 저장한 뒤, 스킬 실행 시 “이전 대화 + 현재 메시지”를 함께 본다.

- 클라이언트: 도구 호출 시 `sessionId`를 A2A params(예: message 메타데이터 또는 별도 필드)에 실어서 전달.
- 서버: `conversationId`로 저장소에서 이전 메시지/응답을 가져와, `SkillExecutor.execute(..., conversationContext)` 형태로 전달.
- 에이전트 내부: 필요하면 **작은 LLM 호출**로 “현재 메시지 + 이전 맥락”을 해석해 주문번호·운송장 추출 후 기존 로직 실행.

**필요한 작업**

- A2A 요청/응답에 conversationId(sessionId) 포함 (스펙/클라이언트 SDK 확인).
- 서버: 세션 저장소(메모리 또는 Redis 등), `*ExecutorProducer`에서 세션 조회 후 executor에 맥락 전달.
- `SkillExecutor` 시그니처 확장: 예) `execute(String userMessage, boolean isInternalCall, List<Turn> recentTurns)`.
- (선택) 에이전트 내부에서 “의도/엔티티 추출”용 LLM 또는 규칙 엔진 도입.

**장점**: 에이전트가 “그 주문”, “그거 취소해줘”를 스스로 맥락으로 해석 가능.  
**단점**: 서버 복잡도·저장소·A2A/클라이언트 수정 필요.

---

### 방안 C: 하이브리드 — 클라이언트가 맥락 요약을 넘김

**아이디어**: 서버는 **여전히 무상태**로, “현재 메시지 하나”만 받되, **클라이언트가 이전 대화를 요약한 문장**을 함께 넘긴다.

- 클라이언트: 도구 호출 전에 “이전 맥락 요약” 생성 (별도 LLM 호출 또는 규칙).  
  예: “이전: ORD-1001 취소 가능 여부 조회함. 사용자: 그럼 취소 진행해줘.”
- 도구 호출 시: `sendRequest(contextSummary + "\n" + currentMessage)` 처럼 한 번에 텍스트로 전달.
- 서버: `extractText`로 받은 **전체 텍스트**를 그대로 `execute(userText, ...)` 에 넘김.  
  에이전트는 이 문자열에서 주문번호·의도만 추출하면 됨 (간단한 파싱 또는 소규모 LLM).

**필요한 작업**

- 클라이언트: 세션별 “맥락 요약” 생성 로직 (프롬프트 또는 기존 대화에서 주문번호/운송장만 추출해 prefix로 붙이기).
- 도구: `sendRequest(..., contextSummary)` 형태로 확장해, 서버로 보내는 텍스트에 맥락 포함.
- 서버: 기존 `execute(userText, ...)` 유지. `userText`에 “이전: … 사용자: …”가 포함되므로, `extractOrderNumber` 등을 “사용자:” 뒤만 보거나, 짧은 의도 분류만 추가하면 됨.

**장점**: 서버는 무상태·세션 저장 없이, 클라이언트만 수정하면 됨.  
**단점**: 요약 품질에 따라 에이전트 해석이 달라질 수 있음.

---

## 3. 권장 방향

1. **단기**: **방안 A**로, 클라이언트의 시스템 프롬프트와 도구만 보강해 “이전 대화 맥락을 활용한 후속 질의”를 처리하게 한다. 에이전트는 계속 단일 입력/단일 출력.
2. **중기**: “취소 진행”, “배송 변경” 등 **액션 도구**를 클라이언트에 추가하고, 서버에 해당 스킬을 구현해 두면, 클라이언트 LLM이 대화 이력 + 도구로 자연스럽게 채팅식 흐름을 이끌 수 있다.
3. **장기**: 에이전트가 스스로 대화 맥락을 이해해야 할 요구가 생기면 **방안 B** 또는 **방안 C**를 검토하면 된다.

이 문서는 `CLAUDE.md`의 세션 기반 채팅 설명과 맞춰 두었으며, 실제 구현 시 `a2a-client`의 시스템 프롬프트·도구와 `a2a-server`의 `SkillExecutor`/`*ExecutorProducer`를 위 방안에 맞게 확장하면 된다.
